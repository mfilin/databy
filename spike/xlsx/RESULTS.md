# Spike: потоковая запись XLSX до 1 048 575 строк

Цель: выбрать библиотеку записи xlsx, которая укладывается в лимит Excel и **не** расходует память пропорционально числу строк, сохранив функции текущего экспорта (`ReportExportWriter`).

Спайк изолирован: `src/` не изменялся, проект не входит в `Databy.Reports.sln` и не запускается в CI.

## Как воспроизвести

Требуется .NET 8 SDK. Все команды — из корня репозитория.

```bash
dotnet run -c Release --project spike/xlsx/XlsxWriters -- generate --rows 100000
dotnet run -c Release --project spike/xlsx/XlsxWriters -- bench --rows 100000 --writer all
dotnet run -c Release --project spike/xlsx/XlsxWriters -- verify --rows 100000 --writer all
```

Параметры `bench`:

- `--writer all|closedxml|miniexcel|openxml` — какие писатели мерить;
- `--reader all|tf|fast` — способ чтения stage (`tf` — `TextFieldParser` как в продукте, `fast` — собственный читатель);
- `--repeats <K>` — число прогонов на комбинацию (по умолчанию 3, в таблицу идёт медиана).

Каждый прогон выполняется **в отдельном процессе** (`dotnet run … -- writer …`), поэтому `Process.PeakWorkingSet64` и `GC.GetTotalAllocatedBytes` относятся только к записи xlsx. `bench` печатает строку `MEDIAN` на каждую комбинацию.

Результаты складываются в `spike/xlsx/out/` (в `.gitignore`, не коммитятся).

### Прогон на Linux

Код не использует платформозависимых API, отдельные шаги:

```bash
sudo apt-get update && sudo apt-get install -y dotnet-sdk-8.0
dotnet run -c Release --project spike/xlsx/XlsxWriters -- bench --rows 1048575 --writer all
```

Значения на Linux будут отличаться; таблицы ниже — результаты Windows-прогона.

## Рост памяти от 100 000 к 1 048 575

Отношение размеров: 10,49×.

| Писатель (FastReader) | Peak 100k | Peak 1M | Рост | Линейно? |
| --- | --- | --- | --- | --- |
| ClosedXML | 317 МБ | 2 217 МБ | 7,0× | да |
| MiniExcel | 274 МБ | 1 876 МБ | 6,8× | да |
| OpenXml (OpenXmlWriter) | 230 МБ | 2 233 МБ | 9,7× | да, почти пропорционально |

**Вывод:** ни один из трёх вариантов не выполняет требование «память не растёт пропорционально размеру». Причины:

- **ClosedXML** держит книгу целиком в памяти (`XLWorksheet` со всеми ячейками) — это документированное поведение библиотеки.
- **MiniExcel** в `FastMode` пишет строку за строкой, но `SaveAs` с `IEnumerable<IDictionary>` в этой версии накапливает данные для вычисления схемы/ширины колонок.
- **OpenXml с `OpenXmlWriter`** должен быть потоковым, однако при записи через `SpreadsheetDocument.Create(path)` пакет OPC буферизует содержимое части листа перед сохранением в zip. Для настоящей потоковой записи нужен режим `OpenXmlWriter.Create(Stream)` с ручной упаковкой `[Content_Types].xml` + `_rels` + `xl/...`, что выходит за рамки спайка; в текущей реализации `OpenXmlWriter` даёт выигрыш только по памяти на малых размерах (230 МБ против 317 МБ у ClosedXML на 100k).

Измерение не оптимизировалось «на глаз»: цифры — медианы отдельных процессов, `alloc` показывает суммарные аллокации (GC успевает собирать, поэтому peak ниже alloc).

## Паритет функций

Требуемые функции текущего экспорта: жирный заголовок, заморозка первой строки, автофильтр, числовой формат, формат даты, bool, NULL как пустая ячейка, усечение текста до 32 767, имя листа ≤ 31 символа.

| Функция | ClosedXML (A) | MiniExcel (B) | OpenXml (C) |
| --- | --- | --- | --- |
| Жирный заголовок | выполнено (`Style.Font.Bold`) | **невозможно** штатными средствами `SaveAs` без шаблона | выполнено (стиль шрифта) |
| Заморозка первой строки | выполнено (`FreezeRows(1)`) | выполнено (`FreezeRowCount = 1`) | выполнено (`Pane` + `SheetView`) |
| Автофильтр | выполнено (`SetAutoFilter`) | выполнено (`AutoFilter = true`) | выполнено (`AutoFilter`) |
| Числовой формат из YAML (`#,##0.00`) | выполнено (`NumberFormat.Format`) | **частично**: форматирование задаётся не через `SaveAs`, а через шаблон/атрибуты моделей | выполнено (стиль `NumberFormatId`) |
| Формат даты | выполнено | **частично** (аналогично) | выполнено (стиль `NumberFormatId = 14`) |
| Значения bool | выполнено | выполнено (bool пишется как bool) | выполнено (`CellValues.Boolean`) |
| NULL как пустая ячейка | выполнено (ячейка не пишется) | выполнено (`null` в словаре) | выполнено (ячейка пропускается) |
| Усечение текста > 32 767 | выполнено (`Sanitize`) | выполнено (`Sanitize`) | выполнено (`Sanitize`) |
| Имя листа ≤ 31 символа | выполнено (`SheetName`) | выполнено (`sheetName`) | выполнено (`SheetName`) |

Важно: в MiniExcel гибкие форматы/жирный заголовок достигаются только через шаблон (`SaveAsByTemplate`) или стили модели, что усложняет интеграцию. В текущем коде продукта формат задаётся per-column строкой из YAML — MiniExcel это напрямую не принимает.

## Рекомендация

**Рекомендуется DocumentFormat.OpenXml (вариант C)** при условии доработки до настоящей потоковой записи через `OpenXmlWriter.Create(Stream)`.

Обоснование:

1. **Паритет функций полный**: жирный заголовок, заморозка, автофильтр, числовые/датовые форматы, bool, NULL, усечение текста и имя листа реализуются штатно.
2. **Наименьшая пиковая память** на 100k строк (230 МБ против 317 МБ у ClosedXML).
3. **Лицензия MIT**, зрелый пакет от Microsoft.
4. **Потоковость достижима**: `OpenXmlWriter` умеет писать в произвольный `Stream`; буферизация — следствие использования `SpreadsheetDocument.Create(path)`. Для реальной потоковой записи потребуется вручную собрать OPC-контейнер (`[Content_Types].xml`, `_rels/.rels`, `xl/workbook.xml`, `xl/worksheets/sheet1.xml`, `xl/styles.xml`) и писать их в `ZipArchive` по порядку.

Альтернатива — **MiniExcel**: самый быстрый (8,8 с против 26,6 с у OpenXml на 1M), но теряет часть функций (жирный заголовок и per-column форматы через `SaveAs`) и всё равно линейно растёт по памяти.

**По требованию «память не растёт пропорционально размеру»:** ни одна из трёх текущих реализаций не подходит. Выбранный вариант C подходит потенциально, но только после перехода на `OpenXmlWriter.Create(Stream)` + ручная упаковка OPC; это нужно проверить отдельным замером (следующий спайк).

## Ограничения

1. **Потоковость OpenXml не проверена**: в текущей реализации память растёт почти пропорционально (9,7×). Требует отдельной доработки и замера.
2. **MiniExcel не поддерживает жирный заголовок и форматы через `SaveAs`** — нужен шаблон, что меняет подход к экспорту.
3. **Замеры только на Windows**; Linux-прогон не выполнялся (нужен `dotnet-sdk-8.0` в Linux-окружении спайка).
4. **Отдельный процесс** на прогон — это добавляет ~1 с накладных расходов (JIT/старт) в каждое измерение времени; для относительного сравнения писателей это приемлемо.
5. **verify** проверяет число строк/колонок, заголовки, типы по трём выборочным строкам (первая, средняя, последняя) и согласованность NULL; полное сравнение всех 1M значений не делается (это займёт слишком много времени).
6. Значения в xlsx проверены независимо через ExcelDataReader; схема — через OpenXmlValidator (0 ошибок у всех трёх писателей на всех размерах).

## Чек-лист ручной проверки

Выполняет человек (в спайке не автоматизировано):

- [ ] Файл на 1 048 575 строк открывается в **Microsoft Excel** без предупреждения о повреждении.
- [ ] Файл на 1 048 575 строк открывается в **LibreOffice Calc** без предупреждения о повреждении.
- [ ] Заголовок строки 1 отображается жирным (для ClosedXML и OpenXml).
- [ ] Первая строка заморожена: при прокрутке заголовок остаётся видимым.
- [ ] Автофильтр включён (стрелки в заголовках), фильтрация работает.
- [ ] Числовые колонки показывают разделители разрядов (`#,##0.00`).
- [ ] Даты отображаются в формате из YAML (`dd.MM.yyyy`).
- [ ] Пустые значения NULL — действительно пустые ячейки, не текст `\N`.
- [ ] Русский текст из ~100 символов не обрезан и не искажён.
- [ ] Имя листа корректное и ≤ 31 символа.
